# OCR 部位自动选择 —— 实施方案 v4（实证修订版）

> **取代** v1 / v2 / v3。前三版是基于代码推断的，**v4 基于真实工单采样 + 生产库实证重写**。
> v3 的核心假设被证伪：匹配思路从「模糊匹配」改为「**结构化解析 + 别名归一**」。

---

## 一、这次调研做了什么

看不了图片（模型限制），改用两个更可靠的间接手段：

1. **OCR 原样采样**：跑 8 张真实工单（HX×3 / ST×3 / FSXR×2），
   用 prompt 强制模型**原样照抄图上文字**（禁止改写/归一），拿到图上真实写法。
2. **生产库实证**：3 门店 / 67 部位 / 5573 工单项 / 1959 张图片 / 各店配置全量读取。

## 三、v3 被证伪的 7 个假设

| # | v3 的假设 | 实证事实 |
|---|---|---|
| 1 | 图上写的是「部位名」 | 是**复合串**：`作业类型 + 分隔 + 部位主体 + 方位 + 程度` |
| 2 | 一对一匹配 | **一对多**：`喷漆右前杠，左后门及拉手，左后杠` = 3 个部位 |
| 3 | L2 模糊匹配（编辑距离）能救 | 差异不是「差一个字」，是**保险杠皮 vs 前后杠**，编辑距离无用 |
| 4 | 不需要方位处理 | 普遍带方位，且两种写法（前缀 `右前门` / 括号 `（右）`） |
| 5 | 每项都该计入幅数 | **大量非喷漆项**：外修/拆装/更换/维修/修复/精洗/配件行 |
| 6 | 用 name 匹配即可 | **name 重复**（下裙×2、倒车镜×2），必须用 code |
| 7 | 补 3 类别名来源能提效 | `paint_standard.alias` 与模板 alias **实际都是 0 条**，补了没数据 |

**结论：瓶颈不在模型、不在匹配算法，而在「没有解析器」。**
模型已经能准确读出文字（采样输出很准），问题是从 `喷漆_后保险杠皮（左）_半喷` 到 `前后杠半喷` 这段没人做。

## 四、新方案：Parse → Filter → Normalize → Match

### P0 行过滤（最先做，收益最大）

按**作业类型前缀**过滤，只保留计入幅数的行：

| 前缀 | 处置 |
|---|---|
| 喷漆 / 补漆 / 点漆 / 喷 | ✅ 保留 |
| 修复 / 维修 / 钣金 | ⚠️ 待确认（多半是钣金，不计幅） |
| 拆装 / 更换 / 外修 | ❌ 过滤 |
| 精洗 / 美容 / 报价 | ❌ 过滤 |
| 含配件码（`HKHA-`、`SA3HK-`、纯大写字母数字串） | ❌ 过滤 |

> **这条是正确性 bug，不只是准确率问题**：不过滤会把拆装/更换/精洗算进幅数。

### P1 结构化解析

统一把一行拆成 5 元组（三店格式用同一套正则适配）：

```
rawText: "喷漆_后保险杠皮（左）_半喷"
   ↓
{ action: "喷漆", body: "后保险杠皮", side: "左", degree: "半喷", qty: null }

rawText: "喷漆右前杠，左后门及拉手，左后杠"
   ↓ 拆成 3 项
[{action:"喷漆", body:"右前杠", side:"右"},
 {action:"喷漆", body:"左后门", side:"左"},
 {action:"喷漆", body:"拉手",   side:null},
 {action:"喷漆", body:"左后杠", side:"左"}]
```

规则：
- 分隔符优先识别 `_`，其次 `:`/`：`，最后无分隔连写
- 方位：提取前缀（左/右/前/后）或括号 `（左）`，**匹配时忽略**（系统部位无方位）
- 多部位：按 `，`/`,`/`、`/`及`/`+`/`.` 切分 —— **注意 ST 用句点分隔**（`前杠.右前雾灯罩`）
- 程度：识别后缀「半喷 / 全喷 / 里外 / 内侧 / 中度 / 轻度」

### P2 部位主体归一化（别名词典，取代 L2 模糊匹配）

从 67 个部位表 + 采样实证，建立**领域别名词典**（不是模糊匹配）：

| 图上写法 | 系统部位 |
|---|---|
| 保险杠皮 / 前杠 / 后杠 / 保险杠 | 前后杠 |
| 门壳 / 前门 / 后门 / 车门 | 车门 |
| 翼子板 | 叶子板 |
| 钢圈 / 轮毂 | 钢圈翻新 |
| 尾盖 | 后盖 |
| 轮眉边 / 轮眉 | 轮眉 |
| 后杠下段 | 保险杠下段 |
| 门拉手 | 门拉手 |
| 包角 / 后包角 | 包角 |

**词典来源优先级**（v3 的错误在这里被修正）：

1. `paint_shop.categoryAliasMap` —— ⚠️ **语义是「Excel 列名 → [code 或 categoryId]」，不是别名词典**。
   其中 `"下裙/包角/尾翼":[...]` 这类**合并列对 OCR 无用**，只有单部位 key（如 HX 的 `前头盖`）可用。
   解析 value 时需同时支持 **code 和 categoryId**。
2. 内置别名字典（`CATEGORY_NAME_ALIASES`，23 标准名/46 别名）
3. 采样实证新增的映射（上表）
4. 学习库（人工校正沉淀）
5. ❌ `paint_standard.alias`、模板 alias —— **实测 0 条，不作为来源**

### P3 程度耦合（关键，v3 完全没考虑）

系统把「程度」做成**独立部位**，不是属性：

- `车门` / `车门半喷` / `车门里外` / `车门内侧`
- `前后杠` / `前后杠半喷` / `前后杠(新)`
- `机盖` / `机盖半喷` / `机盖里外` / `机盖内侧`

所以解析出的 degree 要拼回部位名：

| degree | 拼接规则 |
|---|---|
| 半喷 | `body + "半喷"`（如 前后杠半喷、车门半喷） |
| 里外 | `body + "里外"` |
| 内侧 / 里面 | `body + "内侧"` |
| 全喷 / 中度 / 轻度 / 无 | 不拼接，用基础部位 |

> 注意 HX 的 `前头盖` 体系：`机盖里外` ↔ HX 叫 `前头盖里外`，已在 categoryAliasMap 中。

### P4 匹配到系统部位

- **主键用 `code`，不用 `name`**（name 重复）
- **code 大小写不敏感**：库里混用 `skirt_only` / `SKIRT_SIMPLE` / `skirt_simple`
- `isSpecial=1` 的 9 项（全车外表/全车内外/全车改色/抛光…）**单独分组**，
  不进常规候选列表（它们不是「部位+幅数」结构，混进去会误导模型）
- 命中多个 → 判歧义，推 top3 人工选

### P5 LLM 定位调整

模型不再是「匹配器」，而是**「结构化输出器」**：
- 要求输出 `rawText`（原样）+ `action` + `body` + `side` + `degree`
- 让模型只做它擅长的事：**读图**，解析和匹配由代码做
- 保留编号选择作为增强，但**必须配合 v3 已识别的 cache key 候选指纹修正**

### P6 校正闭环（不变）

人工校正 → 学习库 → 达标转 active → 回写 `categoryAliasMap`。

## 六、待确认的业务规则（影响正确性，需你拍板）

1. **哪些作业类型计入幅数？** 我的判断：喷漆/补漆/点漆 ✅，拆装/更换/外修/精洗 ❌，
   **修复/维修⚠️ 不确定**（钣金工序，但可能含喷漆）。这条错了幅数就错了。
2. **方位（左/右）是否忽略？** 系统部位无方位字段，我建议忽略，但「左后门+右前门」会是 2 幅还是合并？
3. **ST 的幅数串如何解析？** `喷漆前杠，右前叶，右前钢圈 1.2 0.2 0.2` —— 三个数字对应三个部位？
   还是 `1.2` 是总幅、后面是别的意思？
4. **HX 的 `0 150 0` 是什么？** 看起来是金额/工时列，不是幅数。确认后要排除，避免串到 quantity。
5. **`点漆` 算喷漆项吗？**（`点漆右前门边 1 1.2 0.8`）
6. **修复/维修 若含喷漆，是否拆出喷漆部分计幅？**

## 七、关于模型：不用换（v3 之外的补充结论）

- 真实图片量：FSXR 431 + HX 783 + ST 745 ≈ **1959 张 / 8 个月 ≈ 日均 8 张**
- 按 MiniMax-M3 计价 ≈ **¥1~2 / 月**
- 换模型省不到钱，**准确率才是唯一目标**
- 采样显示模型读图很准（配件码、括号方位都读对了），**瓶颈在后端解析，不在模型**

**建议：维持 MiniMax-M3，把精力放在解析器上。**
